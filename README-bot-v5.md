# V5 — 첫 실제 투약·체온 기록에서 정하는 반복 리마인더

## 적용

1. **V3 또는 V4를 적용한 프로젝트**의 SQL Editor에서 `supabase/daddy_bob_jooseyo_v5_upgrade.sql` 전체를 실행합니다. V4와 V5를 한 트랜잭션으로 적용하므로 V4를 따로 실행할 필요가 없습니다. 기존 기록을 유지하고 전용 접두사 객체만 추가·변경합니다. 끝의 `care_plans_created`, `v5_rpc_created`가 모두 true여야 합니다. 과거 설치 SQL을 다시 실행하지 마세요.
2. `n8n/daddy-bob-jooseyo-v5.json`을 새 워크플로우로 가져옵니다. 기본 Google Gemini, Telegram, Supabase의 기존 자격 증명을 선택합니다. **새 Get care reminders에도 Supabase 자격 증명이 필요합니다.**
3. 이전 워크플로우와 스케줄을 Unpublish한 뒤 V5 하나만 Publish합니다. 운영 시스템에 자동으로 반영하지 않았습니다.

## 입력과 확인 예시

- “별이 지금 37.5도야. 앞으로 2시간마다 체온 확인 알려줘.”
- “별이 약이름 2.5ml를 밤 9시에 줬어. 이후 6시간마다 3번 알려줘.”
- 첫 실제 기록이 이미 있다면 “별이 체온 알림을 2시간 간격으로 설정해줘.”
- “별이 약이름 알림 중지해줘.” / “별이 체온 알림 30분 미뤄줘.”
- “현재 건강 알림 보여줘.” 또는 `/care`.

간격은 사용자가 명시한 값만 사용합니다. 약 이름·실제 투여량·단위·체온을 추측하지 않습니다. 첫 실제 기록과 반복 계획을 함께 요청하면 한 번의 확인으로 함께 저장합니다. 기존 기록에 설정만 붙이면 새 투약/측정 행을 만들지 않습니다.

확인 화면에 **기준 시각, 간격, 첫 예정 시각, 종료 시각/횟수**를 표시합니다. 종료 시각·횟수 둘 다 없으면 **중지할 때까지 반복**이라고 명시하고 확인받습니다. 지원 간격은 15~10080분, 알림 횟수는 1~1000회입니다. 이는 구현 지원 범위이며 권장 투약 간격이 아닙니다.

야간 포함 여부를 말하지 않았다면 **밤에도 포함해서 설정 / 낮에만 설정** 중 하나를 선택해야 활성화됩니다. `밤에도 알려줘`, `낮에만`으로도 고를 수 있습니다. 이 선택은 수유의 야간 알림 휴식과 **별도**입니다. 낮에만 선택하면 이 계획의 22:00~08:00 알림을 보류합니다. `응`만 반복하면 첫 한 번만 야간 선택을 요청하고 추가 메시지를 반복하지 않습니다.

## 다음 시각 계산

- 첫 실제 측정/투약 시각 + 사용자가 정한 간격으로 시작합니다. 기준 시각이 과거여서 이미 예정 시각이 지났다면 다음 스케줄 실행에서 한 번만 안내합니다.
- 이후 해당 아이·종류·약의 **실제 기록**을 다시 남기면 그 실제 시각 + 간격으로 다음 알림을 계산합니다. 과거 이력을 나중에 입력해도 기준이 뒤로 가지 않습니다.
- 실제 약명별 계획을 분리합니다. 새 실제 기록은 시간 기준만 갱신하며 계획의 용량을 자동 변경하거나 임상적 적절성을 판단하지 않습니다.
- 알림을 전송했다고 실제 투약/측정했다고 저장하지 않습니다. 기록 없이 예정 시간이 여러 번 지나면 놓친 알림을 몰아서 보내지 않고 한 번 안내한 뒤 다음 미래 시각으로 넘어갑니다. 수신한 투약 알림은 복용 지시가 아니며 마지막 실제 투여 시각과 의료진·약 안내를 확인해야 합니다.
- 지정 횟수는 **성공적으로 보낸 알림 횟수**입니다. 실제 투여 횟수가 아닙니다. 종료 시각·횟수에 도달하면 알림만 중지하며 기존 건강 기록은 유지합니다.

## 전송·미루기·중지

별도 **1분 스케줄**로 확인하므로 15분 수유 스케줄과 독립적입니다. 정확한 초 단위 전달이나 외부 서비스 장애 시 전송을 보장하지 않습니다.

알림 버튼의 **30분 미뤄줘 / 이 알림 중지**는 해당 계획에만 적용됩니다. 미루는 것은 알림 시간 조정이며 약 투여 시각을 변경하는 의학적 지시가 아닙니다. 종료 시각을 넘기는 미루기는 적용하지 않습니다. 직접 명령은 `/carestop 알림UUID`, `/caresnooze 알림UUID 30`이며 UUID는 `/care`에서 확인합니다.

동시 실행을 막기 위해 발송 대상을 2분간 예약합니다. 전송 실패 시 예약 만료 후 재시도하고, 성공한 발송만 완료 처리합니다. 미루기·중지·새 실제 기록은 기존 발송 예약을 무효화해 오래된 완료 응답이 새 시각을 덮어쓰지 못하게 합니다. 다만 외부 전송 직후 DB 완료 기록이 실패하면 중복 알림 가능성이 남습니다.

## 데이터와 의료 범위

전용 `daddy_bob_jooseyo_care_plans`에 계획을 저장하고 실제 기록은 기존 health 테이블에 유지합니다. 기존 테이블의 앱 전용 INSERT 트리거로 실제 기록 시 다음 알림만 갱신합니다. 다른 프로젝트 테이블이나 Auth 설정은 수정하지 않습니다. 개인 계정 제한·RLS·service_role 전용 RPC를 유지하며 아이 전체 삭제 시 그 아이의 계획도 함께 삭제됩니다.

복용량·투약 간격·치료 기간은 사용자가 의료진/약 안내를 바탕으로 정합니다. 앱은 투약 안전성 검증, 중복 약물·성분 판별, 진단을 하지 않습니다. 고열 등 V4의 경고 안내는 첫 기록을 함께 저장하는 경우에도 유지합니다. 모델에 해당 아이의 제한된 실제 기록과 계획 정보가 전달되므로 Gemini의 데이터 정책을 확인하세요.

## 검증

`npm run build:bot && npm run check && npm test`.

임시 PostgreSQL 호환 DB·모의 Gemini 응답·n8n 표현식 파서로 첫 기록과 계획의 원자적 저장, 야간 선택, 실제 기록 후 시각 갱신, 약별 분리, 실패 재시도, 오래된 발송 완료 무시, 횟수·종료·중지·미루기, RLS·삭제 범위를 검증합니다. 운영 API 및 실제 시간 경과에 따른 발송은 게시 후 확인해야 합니다.
