# Daddy Bob Jooseyo V2 — Telegram 전용

기존 개인 봇의 기록을 보존하면서 확인 대화, 조회·수정·삭제, 다자녀, 성장 기록, 조유량 기반 재고 및 구매 알림을 추가합니다. 운영 DB나 n8n에 자동 적용하지 않습니다.

## 적용 순서

1. 기존 Supabase 전용 테이블이 있고 Telegram-only 변경까지 완료된 프로젝트에서 `supabase/daddy_bob_jooseyo_v2.sql` **전체**를 SQL Editor로 실행합니다. 기존 V1 설치 SQL이나 빈 테이블 전용 Telegram-only SQL은 다시 실행하지 않습니다. V2 SQL은 반복 적용할 수 있고 기존 아이·수유·재고 행을 보존합니다. 변경은 `daddy_bob_jooseyo_` 객체만 대상으로 합니다. 다른 테이블·Auth 설정은 수정하지 않습니다.
2. n8n에서 **새 워크플로우**를 만들어 `n8n/daddy-bob-jooseyo-v2.json`을 Import from File로 가져옵니다. 기존 워크플로우는 검증 전까지 보관합니다.
3. Supabase 자격 증명 선택: `Process command`, `Get reminders`, `Mark delivered`.
4. Telegram 자격 증명 선택: `Telegram updates`, `Acknowledge button`, `Send reply`, `Send reminder`. 파일에는 토큰·자격 증명 ID를 넣지 않았습니다. `$env` 접근이 필요 없습니다.
5. **기존 워크플로우를 Unpublish한 다음 새 워크플로우만 Publish**합니다. 같은 봇에는 Telegram Trigger 하나만 사용하고, 이전 알림 스케줄도 함께 중지합니다. 새 스케줄은 Asia/Seoul, 15분 간격입니다.
6. `/help`, `/children`, `/history 별이`로 먼저 읽기 동작을 확인합니다. 이후 실제 수유 시 `/feed 별이 먹은양 조유량`을 보내고 **확인 전에는 행이 생기지 않음**, 취소 시 변경 없음, 확인 시 한 건만 생성됨을 확인합니다. 같은 확인 버튼을 다시 눌러도 추가 저장되지 않아야 합니다.
7. 알림 시각이 지나면 Telegram의 `먹였어요` → 실제 먹은 양과 조유량 입력 → 확인 → 저장을 확인합니다. `아직이에요`는 수유를 생성하지 않고 약 30~45분 뒤 다시 안내합니다. 스케줄 수동 실행과 자동 실행을 동시에 돌리지 마세요.

SQL 적용 후에도 V1 흐름은 당장 깨지지 않지만, **V1에는 V2 재고 보정·중복 방지 로직이 없으므로 병행 운영하지 마세요.** 되돌려야 한다면 새 워크플로우를 중지하고 데이터를 보존한 상태에서 원인을 확인하세요. V2 테이블을 삭제하는 롤백은 제공하지 않습니다.

## 명령

이름은 등록된 이름과 정확히 일치해야 합니다. 아래 숫자는 **문법 예시이며 실제 수유·제품 조유 지시가 아닙니다.**

| 명령 | 동작 |
|---|---|
| `/feed 별이 120 150` | 실제 먹은 양 120ml, 준비한 조유량 150ml. 확인 후 현재 시각으로 저장 |
| `/feed 별이 120` | 먹은 양·조유량 모두 120ml로 가정. 남겼다면 두 값을 입력 |
| `/history 별이` | 최근 10건과 수정·삭제용 UUID, 한국 시간 |
| `/edit UUID 110 150` | 기존 한 건의 먹은 양·조유량 수정. 확인 필요 |
| `/edit UUID 110 150 2026-11-25T19:23:00+09:00` | 시각까지 수정. 명시적 시간대 필수, 미래 시각 불가 |
| `/delete UUID` | 수유 한 건 삭제. 확인 필요 |
| `/children` | 아이 목록 |
| `/childadd 둘째 2026-07-13` | 아이 추가, 기존 같은 이름은 유지 |
| `/growth 별이 6.5 62` | 오늘 체중 kg·키 cm 기록 및 현재 체중 갱신 |
| `/status 별이` | 최근 성장 기록, 최근 24시간 섭취 기록, 체중 기반 참고 범위, 재고 |
| `/stock 별이 제품명 700 5 40 2 3 2` | 재고 기준 교체. 각 숫자 의미는 아래 참고. 확인 필요 |
| `/reset 별이` | 모든 수유 행 삭제, 프로필·성장·재고 유지. 추적된 재고 차감량 복원. 확인 필요 |
| `/childdelete 별이` | 해당 아이 프로필·수유·성장·재고 영구 삭제. 확인 필요 |
| `/cancel` | 대기 중 확인·양 입력 취소 |

수유·수정·삭제·재고 교체 확인은 **15분** 유효하며 한 채팅에 하나만 대기할 수 있습니다. 다른 확인 요청을 만들면 이전 버튼은 만료됩니다. 봇에 숫자만 보내는 것은 `먹였어요` 버튼으로 양 입력을 시작한 경우에만 유효합니다.

## 재고와 구매 알림

`/stock 아이이름 제품명 한통가루g 스푼가루g 스푼당조유ml 남은통수 배송일 여유일`

- 제품명은 공백 없이 입력합니다. 이 명령의 아이 이름도 공백 없이 입력합니다.
- 제품 **라벨의 실제 조유 비율**을 사용하세요. 700은 분말의 **g**이며 한 통이 700ml라는 뜻이 아닙니다. 스푼당 조유 환산량은 제품의 기준에 맞춰 입력하며, 물 용량과 완성량을 혼동하지 마세요. 앱이 제품별 비율을 검증하지는 않습니다.
- `한 통 환산 ml = 한 통 가루 g / 한 스푼 g × 스푼당 조유 ml`.
- `남은통수`에는 `1.5`처럼 부분 사용량을 입력할 수 있습니다. 재고 교체 확인은 기존 값에 더하지 않고 실측 잔량으로 대체합니다.
- V2 기록은 **먹은 양이 아니라 준비한 조유량**만큼 재고를 차감합니다. 재고 설정 전 기록은 소급 차감하지 않습니다. 실측 재고를 다시 설정하면 그 이전 기록의 재고 추적은 종료합니다.
- 재고가 부족하면 수유 저장을 중단합니다. `/history`로 저장 여부 확인 후 실제 잔량을 `/stock`으로 보정하고 수유를 다시 입력하세요.
- 수정·삭제는 마지막 재고 기준 이후의 추적된 차감량만 보정합니다. V1 기록은 실제 차감량을 복원할 수 없으므로 재고에 소급 환불하지 않습니다.
- 최근 최대 7일의 추적된 조유량과 관측 기간(최소 1일)을 이용해 하루 사용량·잔여일을 추정합니다. 기록이 적을수록 오차가 크고 수유 외 분유 사용·유실은 자동 반영되지 않습니다.
- 잔여일 ≤ 배송일+여유일 또는 잔량 ≤ 기본 임계치 1500ml이면 알립니다. 하루 1회로 제한하며, 성공 발송 후에만 타임스탬프를 갱신합니다.

## 성장과 수유량

키는 이력으로 저장하며 수유량 계산에 직접 사용하지 않습니다. `/status`는 생후 7~182일이고 체중이 있을 때만 기존 프로젝트의 150~200ml/kg/일 참고 범위를 표시합니다. 960ml 이상이 계산 범위에 포함되면 소아과 개별 확인 안내를 표시합니다. 이 범위를 목표나 처방으로 사용하지 마세요. 모유·이유식 병행, 미숙아·질환·의료진 개별 지시에는 단순 계산을 적용하지 않습니다. 성장 백분위·성장 이상 판정·자동 수유 처방은 구현하지 않았습니다. 참고 근거는 기존 README의 AAP/NHS 링크를 확인하세요.

## 개인정보·전달 특성

- 현재 개인 채팅·발신자 ID `9114513581`만 허용합니다. DB RPC도 service_role 및 같은 채팅 ID를 확인합니다. 다른 계정으로 바꾸려면 DB 제약과 파서를 함께 변경해야 합니다.
- 신규 테이블도 RLS를 켜고 anon/authenticated 접근을 허용하지 않습니다. Supabase service_role 키는 프로젝트 전체 권한이므로 n8n 자격 증명에만 보관하세요.
- Telegram update_id와 처리 결과를 저장해 재전달 시 DB 중복 변경을 막습니다. 버튼 토큰도 일회성입니다. 자식 전체 삭제 시 캐시된 개인 응답은 지우고 중복 방지 ID는 유지합니다.
- 새 워크플로우는 운영 실행 입출력의 n8n 저장을 끕니다. 이미 저장된 이전 n8n 실행 이력·Telegram 대화·Supabase 백업은 아이 삭제 명령으로 지워지지 않습니다. 해당 서비스에서 별도 관리해야 합니다.
- DB 커밋과 Telegram 전송은 하나의 트랜잭션이 아닙니다. DB 저장 후 답장 실패 시 `/history`로 확인하세요. 알림 전송 성공 후 완료 기록이 실패하거나 스케줄이 겹치면 알림이 중복될 수 있습니다. 분산 전달의 정확히 한 번 발송은 보장하지 않습니다.

## 개발 검증

Node.js 22 이상. 앱 실행 자체는 패키지 설치가 필요 없고, 아래 의존성은 PostgreSQL 호환 PGlite 테스트용입니다.

```sh
npm ci
npm run build:bot
npm run check
npm test
```

테스트는 임시 DB에서 이전 SQL 두 개와 V2 변경을 적용합니다. 운영 Supabase·Telegram에는 접속하거나 알림을 보내지 않습니다. 실제 n8n의 버튼 렌더링, 자격 증명, 예약 발송은 위 적용 순서에 따라 별도 확인해야 합니다.
